# Vibe Coding Cookbook（AI 协作开发经验手册）

> **用途**：积累用 AI（vibe coding）开发本项目时的**坑、经验、有效/无效的做法**。
> **原则**：只记**真实发生过**的事，带具体案例，可操作。不写正确的废话。
> **写法**：每条给"现象 → 原因 → 对策"，能贴提示词就贴提示词。

---

## 0. 总原则（先读这三条）

1. **AI 写得快，但边界守不住。** 平台化项目的命脉在"依赖方向"和"契约"，AI 默认不会守——**必须靠 eslint/CI 强制，不能靠自觉。**
2. **先立规矩，再让 AI 写。** 把 `docs/engineering-spec.md` 喂给它，比事后返工便宜十倍。
3. **AI 会"顺手偷懒"。** 遇到"多实现"它爱用 `if/else` 而不是策略模式；遇到"跨模块"它爱直接 import 而不是发事件。**这些必须点名要求。**

---

## 1. 架构与边界类

### 1.1 AI 爱用 if/else 代替策略模式 ⭐高频

**现象**：让它实现"支持 SQLite/PG/MySQL"，它写出：
```ts
if (dialect === 'sqlite') { ... } else if (dialect === 'postgres') { ... }
```

**原因**：if/else 是最短路径，AI 优先选"能跑"而非"结构对"。

**对策**：提示词里**明确点名策略模式**，并给出三件套结构要求：
> "用策略模式实现，必须包含：① 在 kernel 定义 `StorageDriver` 接口；② 每个方言一个独立实现类，互不 import；③ 一个工厂/注册表作为唯一选择点。**禁止在任何业务代码中出现 `if (dialect===...)`。**"

**验收**：`grep -rn "dialect ===" src/` 应只在工厂里出现。

---

### 1.2 AI 爱跨模块直接 import 实现 ⭐高频

**现象**：计费模块要感知"内容发布"，AI 写出 `import { contentService } from '../content'`。

**原因**：直接调用最直接，AI 不知道你要求"事件解耦"。

**对策**：明确要求走事件总线：
> "模块间通信必须通过 `eventBus.publish/subscribe`，**禁止 import 其他模块的实现**。计费感知内容发布，应订阅 `content.entry.published` 事件。"

**验收**：模块目录里不应出现 `from '../其他模块/'`。

---

### 1.3 AI 会把业务词汇写进内核

**现象**：让它写内核原语，它写出 `interface Article` 或 `publishBlogPost()`。

**原因**：AI 会用最直观的业务词命名。

**对策**：
> "内核**只允许中性原语**：`Entity`、`Field`、`Event`、`Principal`、`Store`。**禁止出现** `article`、`blog`、`order`、`tenant`（业务义）等业务词。"

**验收**：CI 对 `kernel/` 做关键词扫描（见工程规范第 9 章）。

---

## 2. 内容层类

### 2.1 AI 会把渲染产物当数据源 ⭐⭐本项目最痛的坑

**现象**：让它做富文本，它倾向"存 HTML 字符串"，或"存 Markdown 后渲染成 HTML 存起来当数据"。

**原因**：这是最直觉的做法，且网上大量教程这么教。**但它是个真陷阱**——项目早期就吃过亏（博客系统 Markdown→HTML 入库，换主题要重刷全库）。

**对策**：
> "富文本字段**必须存严格遵循 Portable Text 规范的结构化 JSON**，**禁止存 HTML 字符串**。
> HTML 只能作为**可再生的缓存**，永不作为数据源。写入前用 Zod 校验结构。"

**验收**：测试断言 `Array.isArray(entry.data.body) === true`，而非 `typeof === 'string'`。

---

### 2.2 AI 会把可查询数据塞进富文本

**现象**：让它做"商品"，它把价格、库存也写进富文本块里。

**原因**：富文本框"看起来什么都能装"。

**对策**：
> "Portable Text **只装叙述性文本**。任何需要**查询/排序/聚合**的数据（价格、库存、状态）**必须用 `EntityTypeDef` 的普通字段**。"

---

### 2.3 AI 写 Portable Text 时会臆造字段名

**现象**：让它按 PT 格式写，它用 `type`（少下划线）、`id`（不是 `_key`）、`ref`（不是 `asset._ref`）。

**原因**：AI 对 PT 规范的记忆不精确，会"合理推测"。

**对策**：**把规范里的字段名直接贴进提示词**：
> "严格遵循 Portable Text：块用 `_type`/`_key`；文本用 `children: Span[]`；Span 用 `_type:'span'`/`_key`/`text`/`marks`；链接在 `markDefs` 里用 `_key`/`_type:'link'`/`href`；图片用 `asset:{_ref}`。**下划线前缀不能省。**"

---

## 3. 运行时与兼容类

### 3.1 AI 会用 Bun 独有 API 破坏 Node 兼容 ⭐高频

**现象**：因为你说"用 Bun"，它写出 `Bun.serve()`、`bun:sqlite`、`Bun.file`、`Bun.env`。

**原因**：AI 听到"Bun"就默认可以用 Bun 的一切，不知道你有"兼容 Node"的硬约束。

**对策**：**在提示词里贴禁用清单**（见工程规范 6.1）：
> "**禁用** Bun 独有 API：`Bun.serve`→用 Hono；`bun:sqlite`→用 `better-sqlite3`；`Bun.file`→用 `node:fs/promises`；`Bun.env`→用 `process.env`；`bun:test`→用 Vitest。目标：**代码能直接跑在 Node 上**。"

**验收**：CI 扫描禁用 API 的 import。

---

### 3.2 AI 会引入不必要的依赖

**现象**：一个小功能引一个包。

**原因**：AI 倾向"用现成库"而非"用标准库"。

**对策**：
> "**优先用标准库/已有依赖**。每新增一个依赖，先说明'为什么不能少'。内核层依赖需人工批准。"

---

## 4. 文档与记录类

### 4.1 AI 写的"经验总结"往往是正确的废话

**现象**：让它写 cookbook，得到"要注意代码质量""要写好测试"。

**对策**：**要求带真实案例和可操作步骤**：
> "记录每条经验时，必须包含：① 真实现象（贴出错误代码）② 原因 ③ 具体对策（含可复制的提示词）④ 验收方法。"

---

### 4.2 文档职责要提前分清，否则会互相重复

**现象**：dev-log、changelog、cookbook 内容互相抄。

**对策**（本项目约定）：
| 文档 | 记什么 | 视角 |
|------|--------|------|
| dev-log | 做了什么、为什么、遇到什么 | **时间**（流水） |
| changelog | 版本对外变更 | **版本**（结果） |
| cookbook | 坑与经验、有效提示 | **主题**（教训） |

---

## 5. 有效的提示词模式（已验证）

### 5.1 "点名 + 给结构 + 给禁令"三段式

```
① 点名：用【策略模式】实现
② 给结构：必须包含接口/实现/工厂三部分
③ 给禁令：禁止 if (dialect===...)、禁止跨模块 import
```
> 比只说"实现多数据库支持"效果好得多。

### 5.2 "贴规范原文"胜过"描述规范"

涉及 PT、事件命名、契约签名时，**直接把规范里的代码/字段贴进提示词**，别指望 AI 记得准。

### 5.3 "要求写验证测试"倒逼结构正确

让 AI 同时写"可拔插性测试""切方言测试""内容结构断言"——**测试写不出来，往往说明结构没做对**。

### 5.4 先让 AI 复述约束，再动手

复杂任务前：
> "先复述本任务必须遵守的约束（四条宪法 + 禁用 API + 内容铁律），再开始写。"

能显著减少它"写着写着忘了约束"。
