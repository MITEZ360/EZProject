# Vibe Coding Cookbook（AI 协作开发经验手册）

> **用途**：积累用 AI（vibe coding）开发时的**坑、经验、有效/无效的做法**。
> **原则**：只记**真实发生过**的事，带具体案例，可操作。不写正确的废话。
> **写法**：每条给"现象 → 原因 → 对策"，能贴提示词就贴提示词。
>
> **结构**：
> - **第一部分 · 通用准则**：跨项目可复用的 AI 协作方法论（换个项目也能用）。
> - **第二部分 · 本项目准则**：绑定本项目架构/技术栈的约定（换项目即失效）。
>
> 维护：新经验先判断归属——方法论进"通用"，本项目约定进"本项目"，两者可互相引用。

---

# 第一部分 · 通用准则（跨项目可复用方法论）

> 这部分是**个人/团队资产**——换个项目照样管用。

## G1. 总原则（先读这三条）

1. **AI 写得快，但边界守不住。** 只要项目有架构约束，AI 默认不会守——**必须靠 lint/CI 强制，不能靠自觉。**
2. **先立规矩，再让 AI 写。** 把规范文档喂给它，比事后返工便宜十倍。
3. **AI 会"顺手偷懒"。** 遇到"多实现"它爱用 `if/else`；遇到"跨模块"它爱直接 import。**这些必须点名要求。**

> **核心心法**：**契约先行 + 逐层验证 + 约束落到机器。**
> 让 AI 写实现，但**契约和边界必须定死**——定死的载体是**机器可判定的规则（CI / 测试 / 日志）**，而不是"人工审核"。

---

## G2. 契约先行：先定接口，再让 AI 填实现

**做法**：先写出核心契约（interface），确认无误后，再让 AI 逐个实现。

**为什么**：契约是地基。**让 AI 自由发挥数据结构 = 让地基随便长。** 契约定死后，AI 在任何实现上的自由发挥都伤不了根本。

**提示词**：
> "这是已定稿的 `StorageDriver` 契约（贴全文）。请**实现** SQLite 策略，**不得修改契约**。"

---

## G3. 一次只做一层，做完验证再往下

**做法**：严格逐层推进（如：内核 → 存储 → 内容 → 场景），**每层跑通测试再进下一层**。

**为什么**：AI 一口气生成多层代码时，**错误会跨层传播**，且很难定位是哪层的契约理解错了。

---

## G4. 把"约束"变成"可执行的检查"，而不是"口头要求"

**做法**：所有关键约束，**都要能自动判定**（lint 规则、关键词扫描、测试断言）。

**为什么**：**口头约束 AI 会遗忘，CI 不会。** 这是把"规矩"从"记忆负担"变成"机器强制"的唯一办法。

---

## G5. 让 AI 先写"会失败的测试"，再写实现

**做法**：先描述期望行为，让 AI 写测试（此时应失败）→ 再写实现让测试通过。

**为什么**：**测试是"可执行的契约"。** 它能逼 AI 想清楚边界；**测试写不出来，往往说明结构没做对。**

---

## G6. 机器验证优先：测试 + 日志 + CI 判定

> **本心法：不做人工复核 diff**（除非极特殊）。验证一律交给机器——测试（静态）+ 日志（动态）+ CI 规则（边界）。

**原则**：**凡是能自动判定的，绝不靠人。** 判定不了的问题，先想办法把它变成能判定的。

**人工复核 vs 机器判定的对照**：

| 要防的问题 | ❌ 人工看 diff | ✅ 机器判定方式 |
|-----------|--------------|---------------|
| 依赖方向被破坏 | 看 diff | **eslint 边界规则**（越界即报错） |
| 命名/词汇违规 | 看 diff | **CI 关键词扫描** |
| 用了禁用 API | 看 diff | **CI 扫描禁用 import** |
| 改了不该改的文件 | 看 diff | **CI 路径规则**（改动范围校验） |
| 数据结构错 | 看 diff | **测试断言** |
| 架构模式退化成 if/else | 看 diff | **CI 扫描** |
| 契约被偷改 | 看 diff | **契约快照测试** |
| 功能逻辑错 | 看 diff | **单元测试** |
| 运行时报错 | 看 diff | **启动自检 + 日志断言** |

> 结论：**"人工能看出的问题"几乎都能变成 CI 规则或测试。** 把精力花在"把约束翻译成机器可判定的检查"上，而不是审 diff 上。

**日志有两类，都要用**：

**① 运行日志**（程序跑起来时的输出）：
- **启动自检（fail fast）**：启动时打印关键状态，不通过则**直接启动失败**，不带着问题跑。
- **业务路径日志 + 不变量断言**：出现预期外 `ERROR`/`WARN` → 判定失败。

**② 测试日志**（跑测试时的输出，供 AI 和 CI 直接定位）：
```
✓ content.create 返回结构化 body (2ms)
✗ content.create 期望 Array，实际 string
    at test/unit/content.test.ts:42
    expected: Array(5)  received: "<p>hello</p>"
```
> 失败时给出**用例名 + 位置 + 期望 vs 实际**——AI 据此就能直接改，不需要人看。

---

## G7. 测试分层：日常只跑快的

**原则**：**测试要分层，日常只跑单元测试（快）；重装备不常用。**

| 类型 | 定位 | 何时跑 | 耗时 |
|------|------|--------|------|
| **单元测试** ⭐主力 | 隔离、单点、无 IO | 每次提交 | 毫秒级 |
| **启动测试** | 能起 + 自检通过 | 里程碑 / 发版前 | 秒级 |
| **集成测试** | 跨组件、真连库 | 重要变更 / 发版前 | 秒~分钟级 |

**为什么**：**慢测试拖垮迭代节奏。** 日常被集成测试卡住，vibe coding 的速度优势就没了。**重装备不是不重要，是不常用。**

**单元测试的硬约束**（否则它会退化成集成测试）：
- **无真实 IO**：不连库、不发 HTTP、不读 FS——外部依赖一律 fake 注入。
- **单点验证**：一个用例只验一个行为，不串长流程。
- **快**：目标 < 10ms。

**命令分层**（日常快、节点全）：
```bash
bun run verify        # ⭐日常：类型 + 单测（几秒）
bun run verify:full   # 关键节点：+ 启动测试 + 集成测试
```

---

## G8. 报错时给它"完整上下文"，别只贴一行

**做法**：贴错误时，带**文件路径 + 完整报错堆栈 + 相关代码 + 你期望的行为**。

**为什么**：只贴一行报错，AI 会猜上下文，常给出"改对了 A 却改坏 B"的方案。

---

## G9. 圈定任务范围，别让 AI 顺手重构

**现象**：让它改一个函数，它顺手"重构"了三个相邻文件；让它加个字段，它顺手改了表结构。

**原因**：AI 倾向"把看到的都改好"，边界感弱。

**对策**：
> "**只改我指定的文件/函数，其他一律不动。** 若发现别处问题，**先告诉我**，不要直接改。"

**为什么重要**：项目里，"顺手的改动"最可能破坏依赖边界和契约。

---

## G10. 有效的提示词模式（已验证）

### G10.1 "点名 + 给结构 + 给禁令"三段式
```
① 点名：用【策略模式】实现
② 给结构：必须包含接口/实现/工厂三部分
③ 给禁令：禁止 if (dialect===...)、禁止跨模块 import
```
> 比只说"实现多数据库支持"效果好得多。

### G10.2 "贴原文"胜过"描述"
涉及规范、契约签名、字段名时，**直接把原文代码贴进提示词**，别指望 AI 记得准。（例：贴 Portable Text 字段名）

### G10.3 "要求写验证测试"倒逼结构正确
让 AI 同时写验证测试——**测试写不出来，往往说明结构没做对**。

### G10.4 先让 AI 复述约束，再动手
> "先复述本任务必须遵守的约束，再开始写。"
> 能显著减少它"写着写着忘了约束"。

### G10.5 "以旧带新"：给一个已写对的样板，照着写
> "参照 `xxx.ts` 的写法，实现 `yyy.ts`，结构保持一致。"
> **样板比描述更能约束 AI 的风格**，能保证多个实现"长得一样"。

---

## G11. 复用"已验证的提示词"

**做法**：把有效的提示词**存进本手册**，下次直接复用。

**为什么**：提示词的坑只需踩一次；沉淀下来团队共享。

# 第二部分 · 本项目准则（绑定本架构/技术栈）

> 这部分**换项目即失效**——是本项目特有的架构约定。

## P1. 架构与边界

### P1.1 禁止 if/else 代替策略模式 ⭐高频

**现象**：让 AI 实现"支持 SQLite/PG/MySQL"，它写出：
```ts
if (dialect === 'sqlite') { ... } else if (dialect === 'postgres') { ... }
```

**原因**：if/else 是最短路径，AI 优先选"能跑"而非"结构对"。

**对策**：**明确点名策略模式**，给出三件套结构要求：
> "用策略模式实现，必须包含：① 在 kernel 定义 `StorageDriver` 接口；② 每个方言一个独立实现类，互不 import；③ 一个工厂/注册表作为唯一选择点。**禁止在任何业务代码中出现 `if (dialect===...)`。**"

**验收**：`grep -rn "dialect ===" src/` 应只在工厂里出现（已入 CI）。

> **补充：策略表 = 策略模式的轻量版**
> 当分支不是"选谁"而是"同语义字段在各方言怎么写"（二维：逻辑类型 × 方言），用**二维查找表**代替 if/else：
> ```ts
> // ✅ 策略表：加类型/加方言只改一处
> const strategies: Record<LogicalType, Record<Dialect, () => ColumnBuilder>> = {
>   uuid: { sqlite: () => text('id'), postgres: () => uuid('id'), mysql: () => char('id', { length: 36 }) },
> };
> const column = (t: LogicalType, name: string, d: Dialect) => strategies[t][d]()(name);
> ```
> 不写 class，用对象字面量当策略容器。详见 design.md 5.2 与 engineering-spec 5.3。

### P1.2 禁止跨模块直接 import 实现 ⭐高频

**现象**：计费模块要感知"内容发布"，AI 写出 `import { contentService } from '../content'`。

**原因**：直接调用最直观，AI 不知道你要求"事件解耦"。

**对策**：
> "模块间通信必须通过 `eventBus.publish/subscribe`，**禁止 import 其他模块的实现**。计费感知内容发布，应订阅 `content.entry.published` 事件。"

**验收**：模块目录里不应出现 `from '../其他模块/'`（已入 CI）。

### P1.3 禁止把业务词汇写进内核

**现象**：让它写内核原语，它写出 `interface Article` 或 `publishBlogPost()`。

**对策**：
> "内核**只允许中性原语**：`Entity`、`Field`、`Event`、`Principal`、`Store`。**禁止出现** `article`、`blog`、`order`、`tenant`（业务义）等业务词。"

**验收**：CI 对 `kernel/` 做关键词扫描。

### P1.4 分支归属：内核改动必须走 kernel 分支 ⭐

**现象**：AI 默认在当前分支（`main`）上"顺手改一切"，包括 `kernel/` 目录——因为它不知道你有内核/产品分线。

**原因**：AI 没有"这条改动属于哪条长期分支"的意识，默认就是"在当前分支把它做完"。

**对策**：**动手前先告诉它"在哪条分支、改哪一层"**：
> "本次只改**模块/场景层**（走 `main`），**不得触碰 `kernel/`**。
> 如果需要改内核，**停下来告诉我**——内核改动必须另开 `kernel/*` 分支，从 `kernel` 切出、合回 `kernel`。"

**判断口诀**（贴给 AI）：
> "改动对业务场景**无知** → 进 `kernel` 分支；**有关** → 进 `main`。`main` 永不直接改 `kernel/`。"

**验收**：CI 检查"`main` 上是否有触碰 `kernel/` 的提交"。详见 [git-workflow.md](./git-workflow.md)。

## P2. 内容层（本项目最痛的坑区）

### P2.1 禁止把渲染产物当数据源 ⭐⭐（历史教训）

**现象**：让 AI 做富文本，它倾向"存 HTML 字符串"，或"Markdown 渲染成 HTML 后存起来当数据"。

**原因**：这是最直觉的做法，网上大量教程这么教。**但它是个真陷阱**——项目早期就吃过亏（博客系统 Markdown→HTML 入库，换主题要重刷全库）。

**对策**：
> "富文本字段**必须存严格遵循 Portable Text 规范的结构化 JSON**，**禁止存 HTML 字符串**。
> HTML 只能作为**可再生的缓存**，永不作为数据源。写入前用 Zod 校验结构。"

**验收**：测试断言 `Array.isArray(entry.data.body) === true`，而非 `typeof === 'string'`（已入 CI）。

### P2.2 禁止把可查询数据塞进富文本

**现象**：让它做"商品"，它把价格、库存也写进富文本块里。

**对策**：
> "Portable Text **只装叙述性文本**。任何需要**查询/排序/聚合**的数据（价格、库存、状态）**必须用 `EntityTypeDef` 的普通字段**。"

### P2.3 AI 写 Portable Text 时会臆造字段名

**现象**：让它按 PT 格式写，它用 `type`（少下划线）、`id`（不是 `_key`）、`ref`（不是 `asset._ref`）。

**原因**：AI 对 PT 规范记忆不精确，会"合理推测"。

**对策**：**把规范字段名直接贴进提示词**：
> "严格遵循 Portable Text：块用 `_type`/`_key`；文本用 `children: Span[]`；Span 用 `_type:'span'`/`_key`/`text`/`marks`；链接在 `markDefs` 里用 `_key`/`_type:'link'`/`href`；图片用 `asset:{_ref}`。**下划线前缀不能省。**"

## P3. 运行时与兼容

### P3.1 禁止用 Bun 独有 API（破坏 Node 兼容）⭐高频

**现象**：因为你说"用 Bun"，它写出 `Bun.serve()`、`bun:sqlite`、`Bun.file`、`Bun.env`。

**原因**：AI 听到"Bun"就默认可以用 Bun 的一切，不知道你有"兼容 Node"的硬约束。

**对策**：**贴禁用清单**（见工程规范 6.1）：
> "**禁用** Bun 独有 API：`Bun.serve`→用 Hono；`bun:sqlite`→用 `better-sqlite3`；`Bun.file`→用 `node:fs/promises`；`Bun.env`→用 `process.env`；`bun:test`→用 Vitest。目标：**代码能直接跑在 Node 上**。"

**验收**：CI 扫描禁用 API 的 import。

### P3.2 方便与直观 > 极致省空间 ⭐定位红线

**现象**：AI（和人）容易"过度优化"——为了少几百 KB、少一个依赖、少一个文件，写出高度压缩、难以阅读/调试的代码；或把"自包含交付"理解成"必须产出一个单文件"。

**原因**：训练数据里"性能/体积优化"是正反馈，AI 会默认这是优点。

**对策**：**明确项目定位**：
> "本项目定位是**管理复杂度的平台**，**不是**极致省空间的工具。
> 交付目标是**自包含**（目标机器**零环境依赖**：不用装 Node/Bun/nginx/DB），**但形式不限**——单二进制、压缩包、容器**都可以**，**不苛求'必须是一个文件'**。
> 允许的'浪费'：产物大一点（100~300MB）、依赖多一两层、多一个配置文件——只要换来**可读性、可调试性、交付直观**。
> **冲突裁决**：当'省空间/少文件'与'方便直观'冲突，**一律选后者**。"

**应用场景**：
- 不为了省体积而砍掉有用的日志/自检/调试开关。
- 不为了"零依赖"而重写一个已成熟的库。
- 不为了"少一个文件"而把多个关注点塞进一个巨型模块（违背三层洋葱）。
- **不为了"必须单文件"而放弃更易排障的压缩包形式**（如资源多、带插件时）。

**验收**：（无法自动判定）属于**人工把关的少数例外**——评审时若发现"为省而省""为单文件而单文件"的代码，直接打回。

## P4. 本项目的验证约定

### P4.1 机器验证，不做人工复核 diff

**约定**：本项目不收人工复核 diff。验证交给机器：**单测（逻辑）+ 日志（运行）+ CI 规则（边界）**。
本项目落地：四条宪法 → eslint + 扫描；内容铁律 → 测试断言；Bun 兼容 → 禁用 API 扫描。

> 方法论见 **G6**。

### P4.2 测试分层，日常只跑单测

**约定**：日常 `bun run verify`（类型+单测）；启动/集成测试仅在里程碑、发版前跑。
**本项目的验收点**：内核+空模块能启动 → 切方言能生效 → 内容 CRUD 通 → 后台能读。

> 方法论见 **G7**。

### P4.3 本项目的日志样例

**启动自检**：
```
[kernel] 已加载契约: content, storage, authz
[kernel] 已挂载模块: content, storage
[storage] dialect = sqlite (WAL = on)
[selfcheck] OK
```
**业务路径**：
```
[content] create entry type=posts tenant=default
[content] richText 校验通过 (blocks=5)      ← 断言存的是结构
[event] published content.entry.published
```
